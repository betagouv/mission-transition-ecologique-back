# General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax

# TEE POC Backend — Instructions Claude Code

## Projet

Proof of concept backend TEE (Transition Écologique des Entreprises) — ADEME / BetaGouv.
Stack : NX 22 + PayloadCMS 3 + Next.js 15 + PostgreSQL + pnpm 10 + Node.js v24.

## Commandes essentielles

```sh
pnpm nx run @tee-backoffice/cms:dev        # dev
pnpm nx run @tee-backoffice/cms:build      # build
pnpm nx run @tee-backoffice/cms:lint       # lint
pnpm nx run @tee-backoffice/cms:typecheck  # typecheck
pnpm nx run-many -t lint                   # lint tout le workspace
pnpm nx affected -t lint                   # lint fichiers modifiés
pnpm db:up                                 # démarre le Postgres local (Docker, bases `tee` + `tee_test`)
pnpm db:reset                              # remet le Postgres local à zéro (supprime le volume)
pnpm seed                                  # seed complet : operators (groupes, logos) + programs + projects (images) + utilisateurs de dev
pnpm migrate:create <nom>                  # génère une migration Payload (apps/cms/src/migrations/)
pnpm migrate                               # applique les migrations en attente
pnpm migrate:status                        # état des migrations
pnpm test                                  # tests d'intégration (base `tee_test`, Docker requis)
pnpm test:unit                             # tests unitaires (aucune base requise)
pnpm test:libs                             # tests des trois libs (canonical, canonical-store, format-adapters), sans Docker (store sur PGlite) ; job CI « Library tests »
pnpm e2e                                   # tests E2E Playwright (Docker requis)
pnpm data:snapshot                         # rafraîchit la copie locale des fichiers amont (libs/format-adapters/static/upstream/), à commiter
pnpm data:sync:dev                         # sync du CMS depuis l'amont, via nx (charge les .env) : dispositifs, projets, redirections, disparus annulés, rapprochement CMS ↔ canonical
pnpm data:daily:dev                        # pipeline quotidien en local, via nx : sync du CMS, puis Grist (dispositifs seulement)
pnpm import:projects                       # outil de secours : aligne le store canonical des projets sur `static/input/` (fixtures locales), sans Payload ; `--remote` lit l'amont
pnpm seed:scalingo                         # seed sans nx (conteneur Scalingo : `scalingo run pnpm seed:scalingo`)
pnpm scalingo:postdeploy                   # étape postdeploy du Procfile : réinitialise + reseed la base de la préprod, ne fait rien ailleurs

make wt-db-list                            # bases des worktrees (taille, worktree encore présent ?)
make wt-db-drop BRANCH=feat/ma-branche     # supprime la base d'une branche
make wt-db-prune                           # supprime les bases dont le worktree a disparu
```

Chaque worktree créé par le skill `worktree-init` a **sa propre base** `tee_<branche>` : le `make wt-db-*` ci-dessus (script `scripts/worktree-db.sh`) sert à les lister et à faire le ménage. Les bases `tee` et `tee_test` du dépôt principal sont protégées contre la suppression.

Les tests d'intégration et E2E ont besoin du Postgres local (`pnpm db:up`). Les tests d'intégration visent la base **`tee_test`**, vidée avant chaque exécution : ils ne touchent jamais aux données de dev. Le store canonical y utilise le schéma `canonical` de la même base, et les tests du store tournent sur PGlite (Postgres en mémoire), donc sans Docker.

## Seed

**`pnpm seed`** : seed complet idempotent (upsert) : `GeographicAreasSeed` (18 régions + 101 départements) → `ProgramsSync` (operators, groupes et logos d'opérateurs, programs) → `ProjectsSync` (projets et leurs images) → `UsersSeed` (utilisateurs de dev). Les dispositifs, projets et opérateurs (`operators.json`) sont lus sur le **dépôt GitHub amont** (`UpstreamJsonSource.fromSettings(Config.upstreamFallback())`) ; si GitHub est en panne, repli sur la copie versionnée `libs/format-adapters/static/upstream/` **uniquement** avec `TEE_UPSTREAM_LOCAL_FALLBACK=1` dans le `.env` (voir `apps/cms/.env.example`). `docs/sources/` n'est plus lu par le code. Le store canonical est alimenté automatiquement par les hooks : `syncCanonicalOnPublish` quand `ProgramsSync` écrit les dispositifs publiés, `syncProjectCanonicalOnChange` quand `ProjectsSync` écrit les projets publiés (même chemin qu'en prod) : pas d'étape de seed canonical dédiée. **Le seed et la tâche quotidienne partagent la même commande**, `UpstreamSync` (`apps/cms/src/scripts/sync/`, feature 005 lot 4) : `run.ts` l'encadre des zones géographiques et des utilisateurs de dev. Le seed produit donc aussi les documents `remplace` des redirections, annule les disparus de l'amont et finit par le rapprochement CMS ↔ canonical.

### Utilisateurs de dev (`pnpm seed`)

Seedés hors production ; en `NODE_ENV=production`, seulement avec `TEE_SEED_DEV_USERS=1` (`Config.seedsDevUsers()`) : en permanence sur la préprod, au premier seed seulement sur la prod (ADR 0012 §6).

| Email | Mot de passe | Rôle |
|---|---|---|
| `super.admin@tee.test` | `super.admin@tee.test` | `super-admin` |
| `admin@tee.test` | `admin@tee.test` | `admin` |
| `createur@ademe.test` | `createur@ademe.test` | `creator` |

`apps/cms/src/scripts/seed/` ne porte plus que ce qui est propre au seed : `run.ts`, `geographic-areas/` et `users/`. Tout ce qui lit l'amont et l'écrit dans le CMS vit dans `apps/cms/src/scripts/sync/`, partagé par le seed et la tâche quotidienne (rangement du 2026-10-02 : `ProgramsSeed`, `ProjectsSeed` et `SeedErrorFormatter` sont devenus `ProgramsSync`, `ProjectsSync` et `SyncErrorFormatter`).

Dans `seed/` :
- `run.ts` : entrypoint `pnpm seed` : `UpstreamSnapshot.fetch()`, initialisation Payload, `GeographicAreasSeed`, `UpstreamSync`, `UsersSeed`.
- `geographic-areas/` : `GeographicAreasSeed` (régions + départements, fixtures dans `fixtures.ts`).
- `users/` : `UsersSeed`.

Dans `sync/` (feature 005 lot 4, ADR 0014 révision du 2026-10-02) :
- `run.ts` (entrypoint `pnpm data:sync`, première étape du cron ; `--allow-mass-removal`), `UpstreamSnapshot` (tout ce qu'une exécution lit en amont, lu avant le démarrage de Payload : `programs`, `projects`, `rejectedProjects`, `redirects`, `operators`, `assets`), `UpstreamSync` (commande partagée : `ProgramsSync` → `ProjectsSync` → annulation des disparus → rapprochement ; chaque étape tourne même si la précédente a signalé des erreurs, le total sort dans `UpstreamSyncReport.errors` ; options `allowMassRemoval`, `scope` et `reconcile: false` pour les tests d'intégration, qui partagent une base), `GoneDocumentsCanceller` (une seule classe pour les deux collections, `forPrograms` / `forProjects` : documents importés absents du snapshot et non redirigés → `workflowStatus: 'annule'`, écrit en version brouillon comme l'action « Supprimer » de l'admin ; lit les dernières versions ; un document est « importé » quand son `canonicalId` est celui dérivé de son slug, un document créé dans l'admin n'est jamais annulé ; un projet amont écarté pour sa forme n'est pas un disparu ; refus de tout le lot au-delà du plafond d'`UpstreamRemovalGuard`). `CanonicalReconciler` (fin de sync : ligne attendue absente du store = erreur, réécrite à la sync suivante ; ligne que le CMS n'attend pas = retirée sous le même garde-fou ; même règle pour les deux collections : un document est attendu selon `CanonicalSyncPolicy` appliquée à sa dernière version, les états en cours restant « tolérés »).
- À côté, `apps/cms/src/scripts/postdeploy/` : `run.ts` (étape `postdeploy` Scalingo : si `DeployDatabaseResetSettings` l'autorise, `DatabaseSchemaReset` supprime les schémas `public` et `canonical` puis le seed est relancé, les migrations s'appliquant à l'init de Payload en production) ; `DatabaseSchemaReset` sert aussi au global setup des tests d'intégration. Voir ADR 0012 §5.
- `programs/` : `ProgramsSync` (`ProgramsSync.ts`), `OperatorImporter`, `ProgramImporter`. Depuis le lot 4 de la feature 005 : `ProgramsSync` reçoit les redirections (`ProgramRedirects`) et construit les dispositifs `remplace` avec `RedirectTombstoneBuilder` (marqués en place ou clonés depuis leur cible), importés **après** les autres pour que `replacedBy` soit résolu ; `ProgramImporter` n'écrit que sur différence (`UpstreamFingerprint` des données mappées comparée à `upstreamFingerprint` de la dernière version, et présence dans le store canonical : compteur `unchanged`) ; un dispositif laissé en création parce que Payload refuse sa publication n'a pas d'empreinte, il est retenté et signalé à chaque exécution ; le résultat porte `snapshotSlugs` (tous les slugs dont l'amont répond, anciens slugs redirigés compris). Le format brut amont n'est lu que par `TeeImporter` (`libs/format-adapters`, même lecteur que l'import canonical) ; `CanonicalToPayloadMapper` transforme ensuite chaque dispositif canonical en données Payload (`canonicalId` dérivé du slug via `SlugCanonicalId`). Les dispositifs à URL, URL de contact et liens valides sont écrits en `publie` (création validée par Payload : un dispositif qu'il refuse reste en création, signalé en fin de seed), ce qui déclenche le hook `syncCanonicalOnPublish` : le store canonical est peuplé pendant cette étape. Les écritures passent par `SystemWorkflowContext`. Les données que Payload ne peut pas porter (restriction micro-entreprises, liens d'étape « conseiller », montant de financement d'une étude, durée de prêt) sont **signalées en fin de seed**, pas perdues en silence. `OperatorImporter` crée aussi les opérateurs cités dans les variantes. Juste après, si `run.ts` fournit `operators.json` (`OperatorProfilesInput`, absent des fixtures de test) : `OperatorGroupImporter` (upsert des groupes `filterCategories` par slug, logo de secours tiré de `OperatorGroupLogoDefaults` pour 5 groupes, jamais posé sur un groupe qui a déjà un logo) puis `OperatorProfileImporter` (rapprochement par slug du nom ; `groups` **remplacé par la liste amont à chaque seed** ; logo : un upload manuel, média sans `sourcePath`, n'est jamais écrasé, un logo importé suit l'amont et est retiré si l'amont n'a plus d'`imagePath`, un téléchargement en échec garde le logo actuel ; opérateur amont inconnu du CMS signalé, pas créé). Voir ADR 0013.
- `media/` : `UpstreamMediaImporter` (`findOrCreate(sourcePath, alt, category)` : retrouve un média par `Media.sourcePath` et réaligne son `category` s'il diffère, sinon télécharge le fichier amont via `UpstreamAssetSource` et le crée avec ce type (`operator-logo` pour les logos d'opérateurs et de groupes, `project-image` pour les images de projets) ; appels séquentiels ; fichier introuvable ou chemin invalide signalé en fin de seed avec les compteurs créés/réutilisés/recatégorisés/en échec, jamais d'exception ; un chemin en échec n'est pas retenté dans la même exécution). Partagé par les logos et les images de projets : un second seed ne crée aucun média. `ImportedMediaPolicy` : valeur d'un champ upload alimenté par l'amont (fichier posé à la main jamais écrasé, fichier importé remplacé ou retiré selon l'amont, téléchargement en échec sans effet), partagée par `OperatorProfileImporter` et `ProjectImporter`.
- `projects/` (ADR 0014) : `ProjectsSync` (`ProjectsSync.ts`), même chemin que les dispositifs, un seul lecteur du format amont. Depuis le lot 4 de la feature 005 : `ProjectsSync` reçoit les redirections (`ProjectRedirects`), construit les projets `remplace` avec `ProjectTombstoneBuilder` et les importe après les autres ; `ProjectImporter` n'écrit que sur différence (empreinte des données mappées, de l'image et des projets liés tels que le CMS les résout ; `upstreamFingerprint` lu sur la dernière version, comme pour un dispositif : un brouillon laissé en attente par un éditeur est écrasé à la sync suivante ; image et projets liés lus sur la ligne principale ; un projet `remplace` est écrit en `draft: true` ; compteur `unchanged`) ; l'empreinte d'un projet lié n'est posée qu'en passe 2 par `LinkedProjectsUpdater`, qui ne touche pas un projet laissé inchangé. `ProjectsSync` (reçoit les `TeeProject[]` amont et l'`UpstreamMediaImporter`, `fromFile` pour les tests, sans import d'image si le média est omis) passe `projects.json` par `TeeProjectImporter` (`libs/format-adapters`, même lecteur que `import:projects`), puis `CanonicalProjectToPayloadMapper` transforme chaque projet canonical en données Payload (`canonicalId` = `SlugCanonicalId.forProject(slug)`, `_status: 'published'`, relations résolues par `PayloadProjectRelations`, rechargé entre les deux passes). `ProjectImporter` (passe 1 : upsert par slug sous `SystemWorkflowContext`, pour que `assignCanonicalId` prenne l'identifiant fourni ; image calculée via `ImportedMediaPolicy` à partir de `image.chemin_source` : image posée à la main conservée, image importée remplacée ou retirée selon l'amont ; un chemin amont inexploitable (`TeeProjectImporter.unusableImagePaths`, passé par `ProjectsSync`) est quand même tenté, pour qu'il compte comme un téléchargement en échec et garde l'image en place au lieu de la retirer ; **`image` et `linkedProjects` sont toujours écrits**, comme les champs du mapper, pour ne jamais publier la valeur d'un brouillon en attente : `image` reprend la valeur de la ligne principale quand la politique répond « inchangé », `linkedProjects` vaut `[]` si l'amont n'a plus de projet lié, sinon la valeur publiée en attendant la passe 2 ; renvoie la table `canonicalId` → id Payload), `LinkedProjectsUpdater` (passe 2 : `linkedProjects` résolus par `CanonicalProjectToPayloadMapper.mapLinkedProjects`, projet republié, ce qui réécrit sa ligne pivot avec ses liens ; écritures séquentielles : en parallèle, Postgres détecte des deadlocks sur `projects_rels`). Les projets sont écrits **publiés** : le hook `syncProjectCanonicalOnChange` peuple `canonical.canonical_projects` pendant le seed. Les avertissements du lecteur et du mapper (thème inconnu, projet lié ou dispositif introuvable, secteur hors sections NAF, question de FAQ incomplète, chemin d'image invalide) sont affichés en fin de seed (`ImportResult.warnings`) ; un projet sans `theme_principal` reconnu est une erreur. `ProjectMapper` et `types.ts` (`SourceProject`) sont supprimés.
- les deux `run.ts` (seed et sync) sortent en code 1 si les dispositifs ou les projets remontent des erreurs, ou si l'amont porte des projets écartés pour leur forme (`source.rejectedProjects`, listés en fin de seed avec `TeeProjectRecords.describe` : un projet incomplet est une erreur comptée, les autres sont seedés) ; `SyncErrorFormatter` détaille les erreurs (champs d'une `ValidationError`, cause Postgres).

## Structure des apps

- `src/app/(payload)/admin/` — routes UI admin PayloadCMS
- `src/app/(payload)/api/[...slug]/` — routes REST API PayloadCMS
- `payload-types.ts` — généré automatiquement par Payload, **ne pas modifier à la main**

- `src/services/canonical/` : adaptateur CMS et composition root vers le format pivot. `ProgramCanonicalMapper` (Payload `Program` vers `CanonicalProgramInput`, relations peuplées), `ProjectCanonicalMapper` (Payload `Project` vers `CanonicalProjectInput`, projet lu en `depth >= 1` ; `statut_projet` = `remplace` avec `remplace_par` pour un projet `workflowStatus: 'remplace'`, sinon `valide` ; image, dispositifs et projets liés repris par `canonicalId`, une relation restée en id ou sans `canonicalId` est omise ; blocs optionnels vides omis : `priorite`, `faq` sans question complète, `seo`, `description_complementaire` ; `projets_lies` gardé avec `projets: []` s'il porte un titre ou une description), `canonicalMappings.ts` (tables de correspondance Payload ↔ pivot : `THEME_TO_CANONICAL` et son inverse `CANONICAL_TO_THEME`, partagés par les mappers des dispositifs et des projets, types d'aide, montants, durées, bornes d'effectif), `to-payload/` (sens inverse, amont vers CMS : `CanonicalToPayloadMapper` + `CanonicalVariantToPayloadMapper`, relations résolues via le port `ProgramRelations` implémenté par `PayloadProgramRelations` (opérateur par nom, zone par code COG, dispositif remplaçant par identifiant pivot, `refreshPrograms()` entre les deux lots d'import) ; un dispositif amont `remplace` garde `workflowStatus: 'remplace'` et pointe son `replacedBy`, introuvable = erreur ; ne lit que des codes, jamais le vocabulaire amont : géographie depuis `secteur_geographique.structure` (`PAYS-99100` = national ; **les régions priment** : un département d'une région listée est retiré car déjà couvert ; restent alors des régions seules = `regional`, des départements seuls = `departemental`, des régions et des départements d'autres régions = `regional-departemental` ; un code inconnu du CMS va dans `geographicAreaFeedback`), libellés de montant et de durée amont reconnus via `UpstreamAmountLabels` ; renvoie des avertissements pour ce que Payload ne sait pas porter ; pour les projets : `CanonicalProjectToPayloadMapper` (`map(input)` → `{ data, warnings }`, tous les champs Payload sauf `image` et `linkedProjects`, avec `_status: 'published'` et `canonicalId` ; **chaque champ est écrit**, un absent en `null` ou `[]`, car un `update` Payload part de la dernière version, brouillon en attente compris ; `mapLinkedProjects(input)` pour la seconde passe du seed ; un projet amont `remplace` reçoit `workflowStatus: 'remplace'`, `_status: 'draft'` et son `replacedBy`, introuvable = erreur, les autres `workflowStatus: 'publie'`, `_status: 'published'` et `replacedBy: null` ; un secteur hors sections NAF, un dispositif ou un projet lié introuvable deviennent des avertissements, nommés par leur slug ; un `theme_principal` absent lève une erreur), port `ProjectRelations` (`programIdByCanonicalId`, `projectIdByCanonicalId`) implémenté par `PayloadProjectRelations` (`fromPayload`, `refreshProjects` ; un document répond à son `canonicalId` stocké **et** à l'identifiant que le lecteur amont dérive de son slug, `SlugCanonicalId.from` ou `forProject` : un dispositif que le seed n'a pu réécrire qu'en brouillon garde un ancien identifiant sur sa ligne principale et reste lié)), `CanonicalSyncPolicy` (action canonical par `workflowStatus` : `save`/`remove`/`keep` ; **commune aux dispositifs et aux projets**), `rich-text/` (ports `RichTextToMarkdown` / `MarkdownToRichText` + impl Payload `PayloadRichTextToMarkdown` / `PayloadMarkdownToRichText`), `canonicalRepository.ts` et `canonicalProgramService.ts` (singletons mémoïsés qui injectent dans le service domaine `CanonicalProgramService` le repository fourni clé en main par `createCanonicalProgramRepository()` du store, plus le sink d'observabilité ; le CMS ne connaît pas la localisation de la DB canonical), `canonicalProjectRepository.ts` et `canonicalProjectService.ts` (leurs jumeaux pour les projets : `getCanonicalProjectRepository` / `getCanonicalProjectService`, sur le même pool de connexions), `RetryableMemo` (mémoïsation de ces quatre singletons : une promesse rejetée est oubliée, l'appel suivant réessaie au lieu de servir le même échec jusqu'au redémarrage), `observability/` (adaptateurs du port `CanonicalEventSink` : `PayloadLoggerEventSink`, qui journalise aussi les événements `project_*` et distingue un `sync_failed` de projet, « canonical project sync failed », par le champ `entity` ; composition root `canonicalEventSink.ts` = `RoutingCanonicalEventSink` qui route les événements par canal, point d'extension documenté pour Sentry/email/Slack). Voir ADR 0008 et ADR 0014 (projets)
- `src/hooks/shared/` : `beforeChangeWorkflow(collection)` (fabrique du hook de workflow, posée sur `Programs` et sur `Projects` : validation de la transition contre la table de la collection, sync `workflowStatus` ↔ `_status`, remplaçant exigé pour `remplace`, `WorkflowAutomation`, ajout à `workflowHistory` ; l'archivage pose `validityEnd` à la date du jour si elle est vide, AGIR lisant la date de fin et non le statut), `clearUpstreamFingerprint` (beforeChange de `Programs` et de `Projects` : toute écriture hors `SystemWorkflowContext` remet `upstreamFingerprint` à `null`, donc la sync suivante réécrit le document depuis l'amont), `assignCanonicalId` (beforeChange de `Programs` **et** de `Projects` : cuid2 porté dans le pivot, immuable pour les éditeurs ; ### `libs/canonical` — `@tee-backoffice/canonical`

Format **pivot** interne (Canonical Data Model) : TypeScript pur + zod, sans dépendance framework. Source de vérité = zod, types inférés (`z.infer`), clés en français `snake_case` (= format wire). Voir ADR 0007.

**Architecture DDD / hexagonale** (voir ADR 0008 et `libs/canonical/CLAUDE.md`) : ce package est le **domaine**. ## Architecture du code

### Style de code : OOP / Classes

**Toujours préférer le style orienté objet avec des classes** pour la logique métier, les services, les utilitaires et les scripts.

- Encapsuler la logique dans des classes, pas dans des fonctions standalone ou des modules fonctionnels
- Utiliser des interfaces/types TypeScript pour définir les contrats entre classes
- Les fonctions pures et les helpers simples restent acceptables pour les transformations de données triviales (ex: mappers inline dans un constructeur)

### Principes SOLID

- **S — Single Responsibility** : une classe = une seule responsabilité. Une classe = un fichier, nommé identiquement (`ProgressBar.ts` pour `class ProgressBar`). Pas de classes secondaires dans le même fichier.
- **O — Open/Closed** : les classes sont ouvertes à l'extension (héritage, composition) mais fermées à la modification directe. Préférer étendre plutôt que modifier une classe existante.
- **L — Liskov Substitution** : une sous-classe doit pouvoir remplacer sa classe parente sans altérer le comportement attendu.
- **I — Interface Segregation** : préférer plusieurs interfaces spécifiques à une seule interface générale. Ne pas forcer une classe à implémenter des méthodes qu'elle n'utilise pas.
- **D — Dependency Inversion** : dépendre des abstractions (interfaces/types), pas des implémentations concrètes. Injecter les dépendances plutôt que les instancier en dur.

Les classes utilitaires partagées vont dans `src/utils/`.
